# Confronto Windows MCP / Computer Use — 14 settembre 2026

## Decisione

**Windows MCP rimane il motore principale di AIOS su Windows.** Computer Use è
un possibile motore complementare, non il sostituto generale in questa versione.
È una scelta per copertura e controllo del prodotto, NON una vittoria su ogni task.
Sul lungo periodo conviene mantenere un'interfaccia dei motori sostituibile e
promuovere soltanto blocchi deterministici con precondizioni e risultati verificati.
Non implementiamo una migrazione basandoci su un campione piccolo.

## Prove reali

| Prova | Windows MCP | Computer Use |
|---|---|---|
| Blocco note: nuovo documento/salva | 43,7 s; file salvato ma una stringa alterata | 144,0 s; contenuto corretto, recupero avvio e salvataggio |
| Blocco note: riapri/aggiungi/salva | 42,2 s; aggiunta corretta | 79,8 s; aggiunta corretta |
| Antigravity: nuovo file/salva | 152,5 s; primo file vuoto, recuperato | 123,9 s; contenuto corretto, recupero avvio |
| Google Sheets: nuovo foglio/testo/numero/formula | 79,5 s; A1 TEST MCP, A2 21, A3 =A2*2 → 42, salvataggio cloud osservato | Interrotto prima degli input: il runtime non determina l'URL con certezza sufficiente |
| Gmail (prova precedente dello stesso giorno) | 125,2 s; messaggio a se stessi inviato e ricevuto, firma preservata | Interrotto dal controllo URL; nessun invio |

I tempi sono **tempi osservati dell'agente**, includono ragionamento, messaggi e
in alcuni casi letture del codice durante l'attesa. Non sono tempi di uno script
ottimizzato. File JSON allegati contengono timestamp e subtotali delle chiamate
misurate. Le verifiche finali dei file sono state fatte in sola lettura dopo il
salvataggio grafico: non è stato usato il filesystem per simulare gli input GUI.

## Cosa è emerso

- MCP è rapido per screenshot semplici e input. Uno snapshot con albero UI
  nell'editor ha invece reso costoso il recupero (46,6 s insieme al cambio finestra).
- MCP restituisce spesso l'immagine precedente subito dopo un input: il ritorno
  della chiamata non significa che l'app abbia finito. Attendere condizioni di
  stato è diverso dall'inserire ritardi fissi o cliccare senza controllo.
- Il testo MCP `Quantita: 3` è diventato `Quantità:3`. Possibile autocorrezione
  dell'app, non isolata. Un input accettato dal tool non certifica l'esattezza.
- Nell'editor il click dell'agente sul placeholder non ha focalizzato l'area di
  scrittura. Il file era vuoto; la lettura finale lo ha rilevato e il secondo
  tentativo ha prodotto il testo corretto. È un errore di strategia/focus, non
  una prova che il motore non sappia scrivere.
- CU ha riportato due errori di avvio pur avendo aperto le app. Il recupero per
  finestra ha consentito entrambe le prove locali. La scrittura locale è risultata
  esatta in questo campione.
- CU ha bloccato le prove browser per impossibilità di verificare l'URL. È un
  limite osservato del runtime su questa macchina, non un divieto generale di
  usare Gmail/Sheets. Nessun bypass o cambio di motore per aggirare il blocco.

## Strategia medio-lungo periodo

1. Contratto comune: osserva stato, individua target, esegui azione, verifica
   postcondizione. Motore scelto prima dell'esecuzione secondo capacità e policy.
2. Percorso deterministico per parti stabili; IA per ambiguità, valutazioni e
   recuperi autorizzati. Non trasformare coordinate assolute in automazioni
   universali: richiedere identità finestra, layout, focus e condizioni di arresto.
3. Verifiche economiche su ogni effetto rilevante, osservazioni approfondite solo
   dove necessarie. Per scritture distruttive/invii il controllo finale resta.
4. Licenze applicate nel runtime proprio, prima del dispatch, indipendentemente
   dall'adapter. Un plugin esterno non diventa controllabile dalla nostra licenza.
5. Nessun fallback per credenziali o altre azioni vietate dal motore selezionato.
   Si richiede intervento umano. Non abbiamo testato l'inserimento di credenziali.

## Limiti e artefatti

Una prova per scenario e motore, su un solo PC: non è un confronto statistico.
Blocco note CU include avvio a freddo; MCP parte già aperto. Antigravity viene
riavviato con cache calda. Non c'è randomizzazione né normalizzazione della
latenza dell'agente. Non è onesto dedurre “MCP sempre X volte più veloce”.
Il secondo scenario di Blocco note offre un confronto più vicino a pari condizioni.
Non sono state eseguite prove con computer bloccato/spento: “computer chiuso” è
stato interpretato dal contesto come Computer Use.

Sono stati creati solo quattro file di testo in questa cartella e un nuovo
foglio privato “AIOS benchmark MCP 2026-09-14”. I documenti precedenti di Blocco
note e il progetto ripristinato da Antigravity non sono stati modificati. L'editor
è stato chiuso dopo i salvataggi; le schede precedenti di Blocco note preservate.
La mail di benchmark è quella già documentata nel report precedente.
